# PacRuuner

PacRunner is a compiler to convert [pyAmpliCol](https://github.com/MadGraphTeam/pyamplicol)'s recurrence 
mode processes to UMAMI-compatible libraries for both CPU and GPU.

Unified  MAtrix  eleMent  Interface (UMAMI) is a standard interface to bridge various matrix elements 
generators and [MadGraph](https://github.com/MadGraphTeam/MadGraph7) ecosystem. 

## Installation

1. Install [MadGraph7](https://github.com/MadGraphTeam/MadGraph7/).
2. Install `MadGrapg7/madspace`. It should be available from Python: `import madspace as ms`.
3. Install [pyAmpliCol](https://github.com/MadGraphTeam/pyamplicol). It shoud be on the path.
4. Install Julia using juliaup: `curl -fsSL https://install.julialang.org | sh`. 
5. Clone PacRunner, aka `pac-julia`, as `git clone https://github.com/shahriariravanian/pac-julia`.
6. Test Julia installation: `cd pac-julia; julia --project=. -e \"using PacRunner;\"`.
7. Install PacRunner's Python API: `python -m pip install .`.
8. Set `export NVCC=path/to/nvcc`.
  
## Quick Start

Before explaining how PacRunner works, let's run a simple example showcasing the interaction 
between pyAmpliCol and MadGraph. 

Start in a scratch folder. First, we generate a process by running

```
pyamplicol generate "u u~ > z g g" artifacts/zgg --color-accuracy lc --emit-api-bundle
```

Now, `artifacts/zgg` is the artifact folder generated by pyAmpliCol for the "u u~ > z g g" process.
In addition, `artifacts/zgg/API/umami/` contains the source for the UMAMI wrapper. However, it is not 
compiled yet. You can compile it as `make -C artifacts/zgg/API/umami/`, but PacRunner will compile it 
on demand if not available. After this command is executed, the compiled UMAMI driver (`libumami.so` 
or `libumami.dylib`) is placed in `artifacts/.pyamplicol-api-build/zgg/umami/`. 

First, let's see how PacRunner's Python API work. The first example does not use the Julia backend
and runs the stock matrix-element generator:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")   # a is a pyAmpliCol Artifact
process, momenta = a.validation_points()[0] 
batch = momenta[None, :, :]
provider_stock = a.stock()  # the stock provider, i.e., `libumami.so` 
rt_stock = provider_stock.runtime() # the stock Madspace runtime
print(rt_stock(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

Some terminology: An `Artifact` is the output folder of pyAmpliCol or a sub-process of MadMatrix. 
A `Provider` is a unit of computation and `Runtime` means `madspace.Runtime`. The general program
flow is `Artifact -> Provider -> Runtime`. In the previous example, we used the stock provider. Next
example shows how to generate a CPU provider using PacRunner:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")   # a is a pyAmpliCol Artifact
process, momenta = a.validation_points()[0] 
batch = momenta[None, :, :]
provider_cpu = a.compile(device="cpu") 
rt_cpu = provider_cpu.runtime() # the stock Madspace runtime
print(rt_cpu(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

The main change is using `a.compile(device="cpu")` instead of `a.stock()`. This function does the 
following operations:

1. Creating a folder `artifacts/.pacrunner-build/zgg/p0-cpu/`.
2. Exporting the recurrence program using `pyamplicol --export-recurrence` and saving it as `artifacts/.pacrunner-build/zgg/p0-cpu/export.json`.
3. Writing the source files for the CPU provider using `export.json` and the meta data in `artifacts/zgg`.
4. The source files are written to `artifacts/.pacrunner-build/zgg/p0-cpu/programs/0000`.
5. The source folder is compiled to generate `libumami_pac.so`.

We will discuss the files in the source folder below. For now, let's continue with generating CUDA providers. 
PacRunner currently supports two types of GPU backend: `compile(device="cuda")` and `compile(device="cuda_provider")`.
The first one is a hybrid provider, where the UMAMI library identies itself as a "CPU" provider but actually runs CUDA 
kernels. The second one is a full CUDA provider that identifies itself as "CUDA". First, the `cuda` option:

```python
import pacrunner

a = pacrunner.Artifact("artifacts/zgg/")   # a is a pyAmpliCol Artifact
process, momenta = a.validation_points()[0] 
batch = momenta[None, :, :]
provider_cuda = a.compile(device="cuda") 
rt_cuda = provider_cuda.runtime() # the stock Madspace runtime
print(rt_cuda(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

In this example, only the `device` option is changed. The source folder is now `artifacts/.pacrunner-build/zgg/p0-cuda/programs/0000`
and has additional files, which will be discussed below. Next, the `cuda_provider` option:

```python
import pacrunner
import cupy as cp

a = pacrunner.Artifact("artifacts/zgg/")   # a is a pyAmpliCol Artifact
process, momenta = a.validation_points()[0] 
batch = cp.array(momenta[None, :, :])
provider_cuda_provider = a.compile(device="cuda_provider") 
rt_cuda_provider = provider_cuda_provider.runtime() # the stock Madspace runtime
print(rt_cuda_provider(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

Note that for `device=cuda_provider`, we need to pass the momenta wrapped in a CuPy array.

## MadMatrix

The previous examples all used the pyAmpliCol directly to generate matrix elements. However, to find the cross-section, we need
Madspace. We start with generating the process:

```
mg7> generate u u~ > z g g [amplicol]
mg7> output mg7 processes/zgg 
```

We can load the resulting folder using `pacrunner.Output`. Each `Output` has a set of sub-processes,
which can be names using `names` or accessed using `subprocess(name)` or `subprocesses()`. Each
subprocess is a pyAmpliCol artifact with additional metadata. Therefore, we can adopt the same code
as above to generate matrix elements:

```python
import numpy as np
import pacrunner

out = pacrunner.Output("processes/zgg")
a = out.subprocess("A1_uux_zgg")

momenta = np.array([
    [500., 0., 0., 500.],
    [ 500., 0., 0., -500.],
    [142.22002372, -53.10090083, 59.0409804, -74.87149502],
    [380.350097, -268.20692462, 256.15852034, -84.34485361],
    [477.42987928,  321.30782545, -315.19950074, 159.21634863]])

batch = momenta[None, :, :]
provider_cpu = a.compile(device="cpu") 
rt_cpu = provider_cpu.runtime() # the stock Madspace runtime
print(rt_cpu(batch, 0).matrix_element)    # should print [2.43239313e-05]
```

We can use Madspace to calculate a process cross-section:

```python
import pacrunner

out = pacrunner.Output("processes/zgg")
a = out.subprocess("A1_uux_zgg")

provider_cuda = a.compile(device="cuda") 
print(provider_cuda.run().cross_section)    # should print 75.4519586763261
```

Note that passing `cuda` uses the hybrid mode with a CPU interface; therefore, it works with the 
CPU-only build of Madspace. We can do an end-to-end GPU run by passing `device="cuda_provider"`, 
assuming Madspace is built for CUDA.

## pyAmpliCol 1.0.x: RustiCol's recurrence export

pyAmpliCol 1.0.x writes an LC artifact's programs itself: `pyamplicol export-recurrence LC_DIR -o
capture.json`; the format is its `docs/reference/recurrence-export.md`). 

## The compiled folder

| File | What it is |
| --- | --- |
| `runner.c` | the program: `int run(double *out, double *p, const double *momenta)` for one point |
| `runner.h` | its prototype and sizes: `RUNNER_LEGS`, `RUNNER_OUTPUTS`, `RUNNER_ARENA_SIZE` (the scratch `p`) |
| `pacops.c`, `pacops.h` | the sources and instructions |
| `Makefile` | `make` (`runner.o`, `pacops.o`, `testing`), `make clean`; `CC`, `CFLAGS` may be set |

With `interpreter = true`, `runner.c` holds the program as data (the encoded words, sources first, the
edge table and the tables they index, as one `uir_program`) and includes `uirvm.c`, the UIR
interpreter, copied next to it with `uirvm.h`. `run()`, `runner.h` and the values are the same, bit
for bit. The straight-line C is the CPU runner (about twice as fast); the interpreter is the GPU's,
and its CPU build is its test. The interpreter reads each row's fields straight from its word (the
`UIR_` macros of `uirvm.h`) and takes one-word rows only: a program with a wide row (an index beyond
the one-word fields) is refused.

The interpreter's `runner.c` also builds with nvcc: `make gpu` gives `runner_gpu.o` with
`int run_gpu(double *out, const double *momenta, size_t points)` (`uirvm.h`), every point on the GPU,
one thread each, momenta and outputs point by point on the host. Every function of `pacops`, `uirvm`
and the kernels is then a device function too (`PAC_FN`), and the tables are `__device__` data
(`UIR_DATA`). The outputs are the CPU build's bit for bit (`--fmad=false`, as `-ffp-contract=off`).

## Tests

```sh
julia --project -e 'using Pkg; Pkg.test()'
```

Without external tools this tests the loader, the `.sjb` reader, the Complexifier, the Julia runner
against RustiCol's outputs, and, with a C compiler (`CC`, default `cc`), the compiled C: its kernels
are C (`kernel_c`), so every program's folder builds and passes `make test`, and every program runs
in Julia with kernel libraries built from that C. With symjit-utils' `sjb2obj`, the tests also build
the kernels' native libraries: Julia and C against them bit for bit, and each kernel's C against its
library. With nvcc and a GPU, the interpreter's GPU build against its CPU build. With
`PACRUNNER_ARTIFACT` an LC artifact and pac2json installed, its capture:

```sh
SJB2OBJ=/path/to/sjb2obj PACRUNNER_ARTIFACT=/path/to/lc julia --project -e 'using Pkg; Pkg.test()'
```

The C must be built with `-ffp-contract=off` (nvcc: `--fmad=false`): the values are bit for bit only
without contracted multiply-adds.
